Come funziona

RERCaptcha usa CapJS: una sfida di proof-of-work risolta dal browser, senza immagini da riconoscere, senza profilazione dell'utente e senza chiamate a servizi di terze parti durante la risoluzione.

Il ciclo completo di un invio protetto:

{{ code_block( "Browser Tuo server RERCaptcha\n" " │── GET pagina ───────────────▶│\n" " │◀─ HTML + widget.js ──────────│\n" " │\n" " │── POST /{siteKey}/challenge ──────────────────────────────▶│\n" " │◀─ { token, challenge:{c,s,d}, expires } ───────────────────│\n" " │ risolve N proof-of-work (WebWorker + WASM)\n" " │── POST /{siteKey}/redeem { token, solutions } ────────────▶│\n" " │◀─ { success:true, token, expires } ────────────────────────│\n" " │ il widget scrive il token nel campo capjs-token\n" " │\n" " │── POST form (capjs-token=…) ─▶│\n" " │ │── POST /{siteKey}/siteverify ────▶│\n" " │ │ secret + response │\n" " │ │◀─ 200 {\"success\":true} ───────────│\n" " │ │ (il token viene CANCELLATO)\n" " │◀─ risposta applicativa ───────│", 'text' ) }}

Le prime due chiamate partono dal browser verso RERCaptcha direttamente: per questo il servizio deve avere CORS_ORIGIN configurata per il tuo dominio. Solo siteverify è una chiamata server → RERCaptcha e non deve mai partire dal browser: esporrebbe la chiave segreta.

Ottenere le chiavi

Ogni sito riceve una coppia di chiavi. La site key è pubblica e finisce nell'HTML della pagina. La secret key resta sul server: viene mostrata una sola volta al momento della creazione, perché il servizio la conserva solo come hash e non può più mostrartela in seguito.

Le chiavi si richiedono dal pannello di amministrazione del servizio.

Client — widget visibile

Due script, sempre nello stesso ordine, prima del widget:

{# Da qui in avanti sovrascriviamo capjs_public_url/site_key/csp_nonce con placeholder: NON dentro un {% with %}, perché in Jinja un {% set %} eseguito all'interno di un {% with %} resta confinato a quel blocco e non è più visibile fuori (verificato: produce stringa vuota). Fuori da un {% with %}, l'assegnazione sequenziale persiste per il resto della sezione, cosa che qui va bene perché non servono più i valori reali. #} {% set capjs_public_url = 'https://rercaptcha.regione.emr.it' %} {% set csp_nonce = '' %} {% set loader_html %}{% include 'partials/loader.html' %}{% endset %} {{ code_block(loader_html, 'html', nomefile='templates/partials/loader.html') }}

<NONCE> è un segnaposto: rappresenta il nonce generato dal server a ogni richiesta, non un valore da copiare così com'è.

L'ordine non è negoziabile. widget.js legge CAP_CUSTOM_WASM_URL nel momento in cui viene caricato: se la trova vuota, inserisce nella pagina dei <link rel="prefetch"> verso cdn.jsdelivr.net e scarica il modulo WebAssembly da quella CDN pubblica. Per un ente pubblico è traffico verso una terza parte che nessuno ha autorizzato. Verificalo nel pannello Network del browser: non deve comparire nessuna richiesta a jsdelivr.

Il widget:

{% set site_key = 'SITE_KEY_PUBBLICA' %} {% set localizzato = true %} {% set widget_html %}{% include 'partials/widget_visibile.html' %}{% endset %} {{ legenda_segnaposto() }} {{ code_block(widget_html, 'html', nomefile='templates/partials/widget_visibile.html') }}

Il widget crea da sé, al proprio interno, il campo nascosto indicato da data-cap-hidden-field-name e ci scrive il token: basta che si trovi dentro la <form> perché venga inviato con gli altri campi.

Prova dal vivo: captcha visibile localizzato, stesso widget senza localizzazione.

Client — modalità invisibile

La sfida viene risolta appena la pagina è caricata, senza che l'utente interagisca con nulla:

{% set script_html %}{% include 'partials/script_invisibile.html' %}{% endset %} {{ code_block(script_html, 'html', nomefile='templates/partials/script_invisibile.html') }}

new Cap(config), senza secondo argomento, crea il widget con display: none e lo appende a document.documentElement: finisce cioè fuori dalla form. data-cap-hidden-field-name continuerebbe a funzionare, ma scriverebbe in un campo che nessun invio raccoglie — per questo il token va copiato a mano nell'<input type="hidden">, come nell'esempio sopra.

Passando un secondo argomento — new Cap(config, elemento) — piloti invece un <cap-widget> già presente nel DOM, e in quel caso il campo si popola da sé.

Preferisci la modalità visibile quando puoi: quella invisibile impegna la CPU dell'utente al caricamento della pagina senza che se ne accorga, e senza dargli un modo per intervenire in caso di errore. Prova dal vivo: captcha invisibile.

Verifica lato server

Due regole prima del codice:

  1. Verifica sempre lato server. Il token nel campo della form non garantisce nulla finché non è passato da siteverify: chiunque può scrivere un valore a caso in quel campo.
  2. La chiave segreta non lascia mai il server. Non va né nel browser né in un repository pubblico.

Token: monouso e scadenza

Il token è monouso: alla prima verifica riuscita, il servizio lo cancella. Una seconda chiamata a siteverify con lo stesso token restituisce 404 Token not found, indistinguibile da un token mai esistito. Conseguenze pratiche:

  • non verificare mai lo stesso token due volte (attenzione a un middleware e una view che lo controllano entrambi);
  • un retry HTTP automatico sulla richiesta di invio può far arrivare la stessa verifica due volte;
  • su una form multi-step, il token va consumato una sola volta, nello step in cui la verifica è definitiva.

La durata del token (tokenTTL) è configurata per singola site key. Il widget arma da sé un timer sulla scadenza e, quando scatta, svuota il campo nascosto senza avvisare: chi compila una form lentamente vede fallire l'invio con un token mancante e nessuna spiegazione visibile. Gestisci l'evento reset per intercettarlo e mostrare un messaggio.

Cos'è un nonce, e perché serve

Un nonce ("number used once") è una stringa casuale e imprevedibile, generata una volta per ogni risposta HTTP e mai riusata. Serve ad autorizzare uno script o uno stile specifico sotto una CSP restrittiva, senza dover ricorrere a 'unsafe-inline' (che autorizzerebbe qualsiasi script inline, comprese eventuali iniezioni). Il meccanismo:

  1. il server genera un nonce nuovo a ogni richiesta (qui: secrets.token_urlsafe(18) in app.py, funzione _make_nonce) e lo tiene per la durata della risposta;
  2. lo scrive nell'header Content-Security-Policy di quella risposta, come 'nonce-<valore>';
  3. lo ripete identico nell'attributo nonce="<valore>" di ogni <script> (e, se usi style-src con nonce, anche per gli stili) presente in quella stessa pagina.

Il browser confronta i due valori: uno script con un nonce che non combacia (o senza nonce) viene bloccato. Per questo il nonce non può essere una stringa fissa scritta nel codice: se lo fosse, chiunque potrebbe leggerla dal sorgente della pagina e riusarla per far eseguire un proprio script. Va rigenerato a ogni richiesta e passato ai template (qui tramite request.csp_nonce, esposto come csp_nonce in tutti i template — vedi _contesto_comune in app.py). Il placeholder <NONCE> negli esempi di questa guida rappresenta quel valore generato al volo: non va copiato alla lettera.

{{ code_block( "default-src 'self';\n" "script-src 'nonce-' https://rercaptcha.regione.emr.it 'wasm-unsafe-eval';\n" "style-src 'self' 'nonce-';\n" "connect-src 'self' https://rercaptcha.regione.emr.it;\n" "worker-src blob:;\n" "object-src 'none';\n" "base-uri 'self';\n" "form-action 'self';\n" "frame-ancestors 'none';", 'text' ) }}
script-src
Il nonce copre gli script della tua pagina, anche quelli con src esterno: non serve aggiungere 'self'. L'origine del servizio serve perché widget.js inietta a sua volta uno script. 'wasm-unsafe-eval' è necessario per compilare il modulo WebAssembly.
style-src
Il widget inietta un <style> nel proprio shadow DOM. Perché il nonce lo copra invece di ricorrere a 'unsafe-inline', va impostata la variabile window.CAP_CSS_NONCE con lo stesso nonce, prima di caricare widget.js.
connect-src
Necessaria appena introduci default-src: senza, le chiamate a challenge e redeem verrebbero bloccate.
worker-src blob:
Il risolutore gira in web worker creati a partire da un blob.

Accessibilità

Il widget rende un div role="button" tabindex="0" all'interno di uno shadow DOM. Due conseguenze dirette:

  • <label for="..."> non si associa mai a un custom element: non usarla. Se serve un testo di contesto, mettilo adiacente e collegalo con aria-describedby, oppure usa <fieldset>/<legend>.
  • Il nome accessibile arriva solo dalle quattro chiavi *-aria-label della tabella in Attributi del widget. Ometterle non rimuove l'annuncio: lo lascia in inglese.

Da tastiera il widget si attiva con Invio e Spazio.

Gestisci gli errori di verifica con role="alert" e sposta il focus sul messaggio, così chi usa uno screen reader lo percepisce subito.

Un captcha non dovrebbe mai essere l'unico canale di accesso a una funzione: prevedi sempre un percorso alternativo per chi non riesce a completarlo (WCAG, linee guida AGID).

Appendice: widget personalizzati

"Personalizzare il widget" può voler dire tre cose diverse, con soluzioni molto diverse per costo e rischio. Prima di scrivere codice nuovo, verifica quale ti serve davvero.

1. Cambiare aspetto o comportamento del widget ufficiale

Il caso più comune, e quello che richiede meno lavoro: non serve un widget diverso, bastano gli strumenti già del widget ufficiale, già documentati in questa guida.

  • Colori, dimensioni, font → personalizzazione grafica (custom property CSS e ::part()).
  • Testi ed etichette → attributi data-cap-i18n-*.
  • Comportamento del pulsante di invio, barre di avanzamento, gestione dell'errore → eventi solve/progress/reset/error: il widget resta quello ufficiale, la tua UI reagisce ai suoi eventi.

2. Integrarlo in un framework diverso da HTML puro

Il widget è un web component (<cap-widget>): funziona ovunque, ma nei framework a componenti va spesso "svegliato" con la sintassi propria del framework per intercettarne gli eventi. La documentazione ufficiale del progetto CapJS fornisce esempi nativi — senza bisogno di librerie di terze parti — per React 19+, Vue, Svelte 5, SolidJS, Astro, Preact e Qwik. Esempio in React:

{{ code_block( "import { useRef } from \"react\";\n\n" "function CaptchaForm() {\n" " const tokenRef = useRef(null);\n\n" " return (\n" " { tokenRef.current = e.detail.token; }}\n" " />\n" " );\n" "}", 'jsx' ) }}

Per gli altri framework, la sintassi cambia (in Vue è @solve, in Svelte 5 on:solve...) ma il principio è lo stesso: resta il widget ufficiale, cambia solo come lo colleghi al resto della UI. Vedi la pagina widget della documentazione CapJS per lo snippet del tuo framework.

3. Scrivere un client del tutto proprio (widget alternativo, app nativa, CLI)

Qui il widget non c'entra più: si tratta di parlare direttamente con gli endpoint challenge/redeem (vedi come funziona) e risolvere tu stesso la sfida di proof-of-work — per esempio in un'app mobile nativa, o in un widget per un framework non coperto dal punto 2.

L'algoritmo di risoluzione non è documentato qui perché deve combaciare esattamente con quello che il servizio si aspetta: descriverlo a parole rischia di produrre un'implementazione leggermente diversa e quindi incompatibile, in modo silenzioso, alla prima modifica dell'algoritmo upstream. Usa come riferimento il codice sorgente di @cap.js/server (Apache-2.0, nello stesso repository di CapJS) invece di reimplementarlo da una descrizione, e verifica il comportamento contro un'istanza reale del servizio (anche questa demo, in locale) prima di considerarlo pronto. Controlla inoltre la versione: alcune versioni di CapJS supportano anche sfide "a instrumentation" oltre al semplice proof-of-work, che un client scritto da zero potrebbe non gestire.

Per l'uso legittimo da server-to-server (non per un form compilato da persone reali, ma per automazioni o account di servizio che devono comunque superare la verifica) il progetto CapJS pubblica @cap.js/solver: risolve le sfide lato server, gira solo su Bun, non aggira il proof-of-work reale e non supporta le sfide "a instrumentation".
